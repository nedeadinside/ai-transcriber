# Code Review Report: Ai-Transcriber

## Резюме состояния кодовой базы
Проект представляет собой микросервисную архитектуру для транскрибации, диаризации и суммаризации аудио. Основная инфраструктура (Redis, FastAPI, ARQ) настроена логично, присутствует разделение на независимые сервисы и общую библиотеку (`core`). Код написан чисто, с использованием современных возможностей Python 3.12 (аннотации типов, Pydantic для валидации конфигурации и схем данных, FastAPI). Использование линтеров (ruff) помогает поддерживать единый стиль кода.

Однако при детальном анализе выявлен ряд критических проблем, напрямую угрожающих стабильности приложения. Ошибки при работе с `asyncio` (синхронные вызовы тяжелых вычислений блокируют event loop) и неоптимальное управление памятью (загрузка файлов целиком в RAM перед сетевым запросом) приведут к зависаниям и OOM-крашам даже при небольших нагрузках. Также обнаружена SSRF-уязвимость в механизме вебхуков и полное отсутствие автоматизированных тестов, что делает систему хрупкой. Данные проблемы требуют обязательного исправления перед запуском в production.

## Топ-10 приоритетных проблем

1. **Critical:** Блокировка Event Loop в `diarizer` из-за вызова синхронного CPU/GPU-тяжелого инференса PyTorch внутри асинхронного таска.
2. **Critical:** Риск Out of Memory (OOM): Чтение больших аудиофайлов целиком в память перед отправкой по сети в HTTP-клиентах.
3. **Critical:** SSRF-уязвимость в механизме вебхуков из-за отсутствия проверки принадлежности URL к публичным IP-адресам.
4. **High:** Квадратичная сложность $O(N \times M)$ в алгоритме мержа сегментов, блокирующая event loop на несколько секунд.
5. **High:** Безвозвратная потеря результатов транскрибации и диаризации при любой (даже временной) ошибке API-вызова LLM.
6. **Medium:** Абсолютное отсутствие автоматических тестов (`pytest` не находит ни одного теста).
7. **Medium:** Неработающий механизм отмены в DiarizerClient (`await` внутри `except CancelledError` прерывает отправку запроса POST /cancel).
8. **Medium:** Дублирование кода загрузчиков конфигурации (`loader.py`) в обоих микросервисах.
9. **Low:** Выполнение блокирующих I/O операций по удалению файлов (unlink) в асинхронных функциях напрямую.
10. **Nit:** Глобальная настройка логгера (`logging.basicConfig`) внутри фабрики FastAPI, что может конфликтовать с Uvicorn.

## Детальное описание находок

### Critical

- **Severity**: Critical
- **Файл:строка**: `diarizer/src/worker/tasks.py:34`
- **Проблема**: Метод `ctx["diarizer"].run(path)` вызывается напрямую внутри `async def diarize`. Метод `run` выполняет синхронные ресурсоемкие вычисления (`load_waveform`, PyTorch-инференс `self.pipeline(audio)`).
- **Почему важно**: Запуск тяжелого синхронного кода в асинхронной функции намертво блокирует asyncio event loop воркера. Воркер не сможет обрабатывать фоновые пинги (heartbeats) ARQ, принимать задачи на отмену и параллельно обрабатывать другие корутины. Это приведет к зависанию ARQ и таймаутам.
- **Рекомендация**: Выполнять синхронный код в отдельном потоке-экзекьюторе:
  ```python
  segments = await asyncio.to_thread(ctx["diarizer"].run, path)
  ```

- **Severity**: Critical
- **Файл:строка**: `transcriber/src/clients/whisper.py:64` и `transcriber/src/clients/diarizer.py:46`
- **Проблема**: Аудиофайлы загружаются целиком в оперативную память перед отправкой HTTP-запроса: `content = await asyncio.to_thread(file.read_bytes)`, после чего передаются в `files={"audio_file": (file.name, content)}`.
- **Почему важно**: При максимальном размере загрузки в 200 МБ файл займет 200 МБ RAM. При формировании `multipart/form-data` библиотекой `httpx` содержимое продублируется в памяти. При concurrency > 1 это быстро приведет к исчерпанию RAM (Out of Memory) контейнера.
- **Рекомендация**: Использовать потоковую передачу данных, передавая файловый объект:
  ```python
  files={"audio_file": (file.name, open(path, "rb"))} # httpx автоматически читает файл без блокировки
  ```

- **Severity**: Critical
- **Файл:строка**: `transcriber/src/api/routes.py:38` (валидация), `transcriber/src/worker/tasks.py:49` (отправка)
- **Проблема**: Webhook-адреса, предоставляемые пользователем, валидируются только через `pydantic.HttpUrl` (проверка формата). При завершении работы транскрибатор выполняет POST-запрос на эти адреса.
- **Почему важно**: Это уязвимость Blind Server-Side Request Forgery (SSRF). Злоумышленник может указать URL внутренней сети (например, `http://diarizer-redis:6379/`, `http://169.254.169.254/latest/meta-data/` в AWS) и заставить приложение отправить POST-запрос с данными во внутреннюю инфраструктуру, что может спровоцировать изменение состояния внутренних служб или дать информацию об архитектуре сети.
- **Рекомендация**: Реализовать проверку IP-адресов доменов вебхуков (исключить частные сети `127.0.0.0/8`, `10.0.0.0/8`, `192.168.0.0/16`, `169.254.0.0/16`) перед принятием задачи.

### High

- **Severity**: High
- **Файл:строка**: `transcriber/src/pipeline/merge.py:27` (функция `_speaker_at`)
- **Проблема**: Для привязки спикеров к словам (алгоритм `attach_speakers`) происходит линейный поиск по всем сегментам диаризации для каждого слова. Если аудио длится час, то $M$ (слов) $\approx 10\,000$, а $N$ (сегментов) $\approx 1\,000$. Получается $10\,000\,000$ итераций внутреннего цикла в чистом Python.
- **Почему важно**: Данная функция выполняется синхронно прямо в `transcription.run`. Выполнение такого вложенного цикла займет секунды и заблокирует event loop воркера.
- **Рекомендация**: Оба списка (`words` и `speaker_segments`) отсортированы по времени. Сложность нужно снизить до $O(M + N)$ с помощью алгоритма с двумя указателями, либо использовать бинарный поиск по времени старта слов.

- **Severity**: High
- **Файл:строка**: `transcriber/src/pipeline/transcription.py:40`
- **Проблема**: Получение LLM-summary происходит в самом конце работы воркера: `await llm_tasks.summarize(...)`. Если происходит сбой LLM (например, OpenAI возвращает 503 или Timeout), выбрасывается `LLMError`, и ARQ переводит всю задачу в статус `JobFailed`.
- **Почему важно**: При любом сетевом сбое LLM-провайдера клиент безвозвратно теряет дорогостоящие результаты вычислений Whisper и Pyannote (Diarization).
- **Рекомендация**: Перехватывать `LLMError` и завершать задачу как успешную, оставляя `summary: null` (предупредив клиента через webhook), либо внедрить надежный механизм сохранения промежуточных результатов.

### Medium

- **Severity**: Medium
- **Файл:строка**: `tests/` (директория не существует)
- **Проблема**: В проекте нет ни единого теста. При запуске `uv run pytest` в корне, обнаружено 0 тестов.
- **Почему важно**: Не тестируется критическая логика обработки аудио, мерж сегментов с учетом перекрытия, валидация вебхуков и поведение при обрыве связи между микросервисами. Любое изменение кода может привести к регрессиям, которые невозможно отследить до деплоя.
- **Рекомендация**: Покрыть юнит-тестами логику `merge.py`, а маршруты FastAPI (`routes.py`) и воркеры — интеграционными тестами через `TestClient` и моки `httpx.AsyncClient`.

- **Severity**: Medium
- **Файл:строка**: `transcriber/src/clients/diarizer.py:84`
- **Проблема**: В методе `_poll` при отмене задачи перехватывается `asyncio.CancelledError`, внутри которого выполняется `await self._cancel(...)`. Внутри `_cancel` происходит вызов HTTP-клиента через `await`.
- **Почему важно**: Поскольку текущая таска уже имеет статус отмененной, вызов любого блокирующего/ожидающего метода (await) моментально породит новую ошибку `CancelledError`. Таким образом, запрос `POST /cancel` до сервиса диаризации никогда не дойдет.
- **Рекомендация**: Выполнять POST-запрос на отмену в фоновой, не зависящей от текущего контекста отмены (shielded) задаче:
  ```python
  asyncio.create_task(self._cancel(job_id))
  ```

- **Severity**: Medium
- **Файл:строка**: `transcriber/src/config/loader.py` и `diarizer/src/config/loader.py`
- **Проблема**: Код функции `load_config` (вместе с `@lru_cache`) дублируется побайтово в двух сервисах.
- **Почему важно**: Нарушение принципа DRY. При необходимости внедрить перезагрузку конфигурации без рестарта приложения придется вносить одни и те же изменения во всех местах.
- **Рекомендация**: Вынести обобщенный конфигуратор в общую директорию `core/src/core/config` и инжектить нужный класс (`AppConfig`) в качестве аргумента к универсальному загрузчику.

### Low / Nit

- **Severity**: Low
- **Файл:строка**: `transcriber/src/worker/tasks.py:91` и `diarizer/src/worker/tasks.py:40`
- **Проблема**: В блоках `finally` удаление временного файла из spool выполняется синхронно: `Path(path).unlink(missing_ok=True)`.
- **Почему важно**: Операции I/O с диском являются блокирующими. Удаление может вызвать микро-задержку event loop при высокой дисковой утилизации.
- **Рекомендация**: Использовать `await asyncio.to_thread(Path(path).unlink, missing_ok=True)`.
